Building the sports-market arbitrage matcher

A rolling walkthrough of what exists, why it was built, what production data taught us, and what comes next.

Project goal and safety boundary

Discover sports contracts on Kalshi and Polymarket, normalize them into a shared representation, and eventually identify pairs whose payouts are genuinely complementary. The current system is deliberately read-only: it uses public production data, stores no credentials, and cannot place trades.

Scope

Union of every sports league and market family found on either venue, including live markets and unusual propositions.

Matching standard

Resolution rules govern. Similar titles are not enough; missing or differing material rules require review.

Current phase

Reliable acquisition and conservative canonical projection. Automated matching and execution are not enabled.

Run the system

The project targets Python 3.12+. No API credentials are needed for these commands.

# Verify public connectivity
PYTHONPATH=src python3 -m arbs.connectivity

# Small production capture
PYTHONPATH=src python3 -m arbs.ingest \
  --max-kalshi-series 3 --max-polymarket-sports 3

# Complete union capture
PYTHONPATH=src python3 -m arbs.ingest

# Normalize and report coverage
PYTHONPATH=src python3 -m arbs.normalization data/raw/sports-<timestamp>.jsonl

# Retry only failed containers from a partial capture
PYTHONPATH=src python3 -m arbs.ingest \
  --resume data/raw/sports-<timestamp>.jsonl --retry-errors

# Test
PYTHONPATH=src python3 -m unittest discover -s tests -v

Raw and normalized production snapshots are intentionally ignored by Git. They are large, volatile runtime artifacts—not source code.

Rolling implementation timeline

Milestone 1

Equivalence rules defined Complete

Specified exact, review, no-match, unsupported, and unpaired decisions. Added market-family taxonomy, live-market gates, machine policy, and adversarial fixtures.

Milestone 2

Production connectivity established Complete

Connected to public Kalshi market/order-book endpoints and Polymarket Gamma/CLOB endpoints. Added verified TLS, bounded retries, request timing, and smoke checks.

Milestone 3

Sports union ingestion built Complete

Implemented Kalshi Sports-series discovery and Polymarket sports-tag discovery, full pagination, immutable payload hashes, and atomic JSONL snapshots.

Milestone 4

Full catalog captured and recovered Complete

The first exhaustive pass exposed Kalshi rate limiting. Partial results were preserved, only failed series were retried at lower concurrency, and the recovered snapshot completed with zero errors.

Milestone 5

Canonical streaming normalization Complete

Added bounded-memory normalization for venue IDs, taxonomy, time, status, outcomes, prices, rules, resolution sources, and source hashes.

What the data taught us

  • Global market feeds are not adequate sports discovery mechanisms; venue-specific taxonomies are required.
  • Kalshi uses broad labels such as basketball and soccer, while Polymarket frequently uses league codes such as NBA and EPL. Canonical mapping must precede overlap analysis.
  • Large Polymarket events embed child markets, so future captures store that information once to reduce snapshot size.
  • Some records lack start or close times. Missing timing data must block deterministic event matching unless corroborated elsewhere.
  • Market-type coverage is much broader than basic moneylines; classification must be explicit and extensible.

Next milestone

Build canonical sport, league, participant, and event identity. The immediate work is to map venue taxonomy into shared IDs, extract participants and time anchors, produce candidate event groups, and measure how many records remain ambiguous. Only then should deterministic contract matching begin.

  1. Create versioned sport and league aliases.
  2. Extract participants without substring guessing.
  3. Normalize home/away and event-stage identity.
  4. Generate candidates using league, participant set, and the agreed ±15-minute window.
  5. Emit evidence and rejection reasons for every candidate.

This page is intentionally rolling: each completed milestone should append evidence, commands, measured results, design changes, and the next safe boundary.
