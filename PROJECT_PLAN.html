Implementation blueprint · MVP

Kalshi ↔ Polymarket Arbitrage Matcher

A deterministic, auditable path from raw sports markets to verified cross-venue matches and executable arbitrage signals.

1. Start with a deliberately narrow MVP

The first release should match only unambiguous, head-to-head, pre-game sports winner markets. It should produce opportunities for human review—not place trades. This gives us exact inputs, explainable decisions, and a clean way to measure false positives.

In scope

  • One sport and league initially (for example, NBA)
  • Moneyline / game-winner binary outcomes
  • Scheduled, pre-game markets
  • Two named teams, a known start time, and no draw
  • Read-only market and order-book ingestion

Out of scope

  • Props, spreads, totals, futures, parlays
  • Markets with overtime-rule differences
  • Live or already-started games
  • Automated order submission
  • Fuzzy or LLM-only matching

MVP success

  • ≥99% precision on accepted matches
  • Every match has a reason trail
  • Zero stale opportunities shown as executable
  • Fees, depth, and slippage included
  • Resolution-rule mismatches are rejected

Core principle: matching titles is insufficient. Two markets are equivalent only when the outcome predicate, event, cutoff, cancellation policy, and resolution rules align.

3. Step-by-step implementation

1

Write the contract-equivalence specification

Before coding, define the exact predicate being compared: “Team A wins Game G under rule set R.” Document treatment of overtime, postponement, cancellation, venue changes, stat corrections, and listed pitchers/players if applicable.

  • Create an acceptance checklist.
  • Define hard rejects versus review-required cases.
  • Record venue terms and API usage constraints.
Deliverable: docs/equivalence.md
2

Build read-only venue adapters

Fetch active markets and best available order-book levels through official endpoints. Preserve the complete response, retrieval timestamp, endpoint/version, and request parameters. Add retries, rate-limit handling, pagination, and strict timeouts.

  • Expose the same adapter interface for both venues.
  • Never infer executable price from a displayed midpoint.
  • Use decimal arithmetic, not binary floating point.
Deliverable: replayable raw snapshots
3

Create a canonical sports event model

Normalize both venues into league, participants, scheduled start, market type, outcome side, and resolution metadata. Keep normalized values separate from source values.

  • Convert timestamps to UTC; retain source timezone.
  • Map teams using maintained league-scoped aliases.
  • Represent home/away separately from outcome ordering.
Deliverable: validated normalized contracts
4

Add authoritative event identity

Where possible, map each venue market to a canonical event supplied by a trusted sports schedule feed. This avoids relying on titles and resolves abbreviations, start-time drift, and home/away ordering.

  • Key candidates by league + participant set + time window.
  • Use external event IDs as corroboration, not resolution authority.
  • Quarantine doubleheaders and ambiguous reschedules.
Deliverable: canonical_event_id mapping
5

Implement deterministic matching

Generate candidates only inside the same league and nearby start-time window. Apply hard equality checks, then explicit resolution-policy checks. Return MATCH, NO_MATCH, or REVIEW with structured reason codes.

Deliverable: auditable match records
6

Normalize order books and fees

Convert contracts into a common $1 payout representation. Model asks for YES and NO by quantity, fee schedule, minimum tick, and venue-specific rounding. Store snapshots atomically so prices compared together were observed together.

Deliverable: executable cost by quantity
7

Calculate opportunities conservatively

Evaluate both directions: Kalshi YES + Polymarket NO, and Polymarket YES + Kalshi NO. Walk each order book to a common fill quantity. Subtract all known fees and a configurable safety buffer.

Deliverable: ranked opportunity records
8

Build review and observability tools

Start with CLI tables or a small read-only web page showing source links, rules, timestamps, book depth, calculation details, and rejection reasons. Log latency, adapter failures, unmatched-market counts, and match-rate changes.

Deliverable: human-verifiable scanner
9

Shadow-run before execution

Run continuously without trading. Save every signal, subsequent price movement, theoretical fill, and final resolution. Manually review all accepted matches and a sample of rejects for at least several hundred events.

Gate: measured precision, recall, and net profitability
10

Add trading only as a separate subsystem

After validation, design execution around partial-fill and legging risk, position limits, kill switches, balance checks, idempotency, reconciliation, and venue access requirements. Cross-venue trades are not atomic; “locked profit” is only locked after both legs fill.

Later phase—not part of MVP

4. Deterministic sports matching

Canonical identity

event_key = (
  sport, league,
  sorted([canonical_participant_a, canonical_participant_b]),
  scheduled_start_utc_bucket,
  event_stage_or_game_number
)

contract_key = (
  event_key,
  market_type,           # GAME_WINNER
  selected_participant,
  includes_overtime,
  void_policy_version
)

Decision sequence

OrderCheckResult on failure
1Both contracts parsed as supported GAME_WINNERReject
2Sport and league are identicalReject
3Canonical participant sets are identicalReject
4Start times are within tolerance (initially ±15 minutes)Review; reject if another candidate exists
5Game number, stage, and home/away details do not conflictReject
6Selected outcome maps to the same canonical teamReject
7Overtime, postponement, cancellation, and rescheduling rules alignReject or review
8Both are open, pre-game, and sufficiently freshDo not price
9Exactly one candidate survives all checksAccept; otherwise review

Alias registry

Aliases must be league-scoped and version-controlled. For example, NBA:LAL, “LA Lakers,” and “Los Angeles Lakers” may map to one canonical ID. Never use unrestricted substring matching: “New York” is not a team identity. Unknown aliases go to review rather than being guessed.

Structured evidence

{
  "decision": "MATCH",
  "matcher_version": "sports-v1",
  "confidence": "DETERMINISTIC",
  "checks": [
    {"code": "LEAGUE_EQUAL", "passed": true, "value": "NBA"},
    {"code": "PARTICIPANTS_EQUAL", "passed": true},
    {"code": "START_DELTA_SECONDS", "passed": true, "value": 0},
    {"code": "RESOLUTION_POLICY_EQUAL", "passed": true}
  ]
}

5. Executable arbitrage calculation

For a common quantity q, one YES and one NO pay exactly q × $1 only if the contracts are truly complementary. Calculate using executable asks at each depth level:

gross_payout(q) = q
total_cost(q)   = cost_to_buy_yes(q) + cost_to_buy_no(q)
net_profit(q)   = gross_payout(q) - total_cost(q)
                  - venue_fees(q) - settlement_costs(q)
                  - safety_buffer(q)
net_roi(q)      = net_profit(q) / total_cost(q)

Example

Buy 100 YES at $0.43 and 100 NO at $0.52. Gross cost is $95; payout is $100. The apparent $5 edge is valid only after fees, rounding, sufficient depth, fresh quotes, and both fills.

Signal gates

  • Quote age below threshold
  • Minimum net profit and ROI
  • Minimum common depth
  • Settlement horizon limit
  • Rules verified and match not under review

Risk labels

  • PRICE book may move
  • FILL one leg may fail
  • RULE resolution divergence
  • CAPITAL funds locked until settlement

7. Verification strategy

  • Golden fixtures: hand-label known matches, non-matches, and ambiguous cases.
  • Unit tests: aliases, timezones, order reversal, decimal rounding, fee tiers, and depth walking.
  • Adversarial tests: same teams on consecutive days, doubleheaders, postponed games, neutral sites, women’s/men’s teams, tournaments, and ambiguous city names.
  • Property tests: participant ordering must not change event identity; adding fees must never improve profit.
  • Replay tests: recorded snapshots must yield identical decisions for a pinned matcher version.
  • Resolution audit: compare both venues after settlement and investigate every divergence.

Release gate: optimize precision before recall. Missing an opportunity costs nothing; accepting a non-equivalent pair can create an unhedged loss.

8. Suggested four-week kickoff

Week 1 · Foundations

Equivalence spec, repository scaffold, schemas, recorded fixtures, one adapter, canonical team registry.

Week 2 · Matching

Second adapter, schedule mapping, deterministic rules, evidence records, golden tests.

Week 3 · Pricing

Order-book snapshots, fee models, depth-aware calculations, staleness gates, scan CLI.

Week 4 · Shadow run

Continuous read-only collection, review screen, metrics, resolution audit, error analysis.

First engineering tickets

  1. Initialize Python package, linting, type checking, and tests.
  2. Define RawMarket, CanonicalEvent, Contract, and OrderBook types.
  3. Capture and sanitize 20 representative market payloads per venue.
  4. Create NBA team IDs and explicit alias mappings.
  5. Implement title-to-structured-contract parsers with failure reason codes.
  6. Write 50 labeled match/non-match fixture pairs before matcher implementation.
  7. Implement the strict matcher and decision evidence.
  8. Implement depth-aware decimal price math and fee interfaces.
  9. Add ingest, match, and scan CLI commands.
  10. Start the read-only shadow run and review every accepted pair.

Expansion order: additional no-draw leagues → draw-capable sports with three-way modeling → spreads/totals → futures and propositions. Each new market family needs its own equivalence specification and fixture corpus.
